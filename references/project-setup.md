# Install or reuse a project's preference skill

Use for an authorized new project, a requested rollout, or a missing link in an existing project's working copy. The agent chooses and performs writes; the helper only reports identity and paths. Do not install a daemon, hook, automatic transcript watcher or independent background writer.

1. Run `locate --cwd <actual-project-root>`. Reuse a matching profile. Keep one profile for all linked Git worktrees. For a non-Git project, choose its actual root explicitly with `--project-root`. A generated chat/scratch folder is not automatically a new project.
2. When no profile exists, use the returned `suggested_profile`, `skill_name` and `identity` as the starting point. Create the private directory with owner-only access. Save `identity.json` and adapt [the project skill template](../templates/project-SKILL.md) and [the root template](../templates/project-user-preferences.md). Create only branches that have real content. The identity has schema version 1, project name, main/alternate roots, Git common directories, normalized credential-free remotes, and its local skill name.
3. Keep the generic protocol in `learned-user-preferences`; the project's skill holds its scope, local evidence and references. It is a distinct project skill, not another copy of the framework. Make it available in the host's supported repo skill directory. For Codex, a folder symlink at `<checkout>/.agents/skills/<skill-name>` can point to the private profile. Symlinked skill folders are supported by [Codex skill discovery](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills). Add the exact symlink path (without a trailing slash) to that repository's local `.git/info/exclude` before linking, and verify `git check-ignore` and `git ls-files` afterward. Preserve any existing skill or unexpected path; never overwrite it. If supported local linking is unavailable, keep the global resolver route and report that project-specific discovery is unverified.
4. For linked worktrees, use the same target and skill name. An existing link into another path is not permission to replace it. Avoid following parent-directory symlinks into unrelated repositories or global skill collections. New worktrees can use the globally installed framework's resolver immediately; link their project skill during the next authorized project setup/use.
5. Point the root at existing instructions and decision sources without copying unverified summaries into quotes. State coverage, for example: “Recording started today. Earlier conversations have not been exhaustively imported; existing guidance is linked below.” Only add preference entries whose evidence was actually read. A created but empty history is not an historical backfill.
6. Keep the root small. Put detailed topic/file examples below `preferences/`, with one canonical location for each entry and cross-links when several aspects are involved. The helper derives the branch map live; do not maintain a parallel snapshot or copied list of project records.
7. Check the profile, resolve it from the main checkout and another linked worktree where available, and verify discovery without launching domain actions. Preserve staged/unstaged work. Ensure the private store is covered by the user's existing private backup policy; do not assume a new top-level folder is included. Backups must retain their credential exclusions/scanning and existing scheduling.

The framework is public; project identities, quotes, examples and source pointers are private. Publish only reviewed framework files and fictional fixtures. Never commit a local project link or private profile to a public repository as an installation shortcut.
